## 2. Metodologia da Auditoria

### Estrutura Geral (Witty-Falcon: 5 Fases)

| Fase | Nome | Escopo | Automação |
|---|---|---|---|
| **1** | Infraestrutura | Instalar tools (knip, dep-cruiser, jscodeshift, gitleaks, lockfile-lint), remover madge, fix sop-audit.sh, configurar eslint plugins, gerar baseline | Automatizada |
| **2** | Correções em lote | 10 TSC errors, 398 ESLint warnings, 548 `let`→`const`, 143 unused exports, items restantes (F2) | Automatizada |
| **3** | Systemic (semi-auto) | F1: Contract map, F4: Presence gaps, F5: Consistency sweep | Semi-automatizada |
| **4** | Feature Audit Completa | ~90 features通过 completo pipeline (T1-T20 + 7 Dimensões) | **Manual** |
| **5** | Validação Final | Formula Type Registry, Test Coverage, Quality Gate, CI Monitoring | Julgamento |

### Pipeline Per-Feature (7 Etapas)

Cada feature segue este pipeline sequencial:

1. **Mapping** — Encontrar todos os arquivos que tocam a feature (`rg -l`)
2. **T1-T20 Audit** — 20 categorias de auditoria (binary outcome + gap description)
3. **7 Dimensions Audit** — Isolamento, Robustez, Best Practices, Implementação, Métricas, UX, Deep Test
4. **Gap Registration** — Cada falha vira gap (G1, G2...) classificado por severidade
5. **Root-Cause Correction** — Correção na origem; proibidos: workarounds, debts, shims
6. **Integration Tests (FT-xx)** — Criar/atualizar testes seguindo padrão estabelecido
7. **Validation** — `tsc --noEmit` = 0, `vitest run` = 100%, `lint` = 0

### As 7 Dimensões de Avaliação

| Dim | Nome | Avalia |
|---|---|---|
| D1 | Test Isolation | tmp dir, cleanup, mocks, side effects |
| D2 | Robustness | Typed contracts, Zod schemas, edge cases |
| D3 | Best Practices | SRP, Dependency Wall, sem workarounds |
| D4 | Optimal Implementation | Simplicidade, sem duplicação, sem dead code |
| D5 | Metrics (Normative) | Metric inventory, fórmulas, compliance (ISO/ISTQB/DORA/OWASP) |
| D6 | UX | Erros acionáveis, CLI help, report readability |
| D7 | Deep Test Audit | 12-item check: bad patterns, Oracle Problem, mock discipline |

### Regras Metodológicas Invioláveis (R1-R5)

| Regra | Descrição |
|---|---|
| R1 | **Dados fictícios estritos** — testes usam mocks explícitos, nunca dados de produção |
| R2 | **Validação contra business logic** — valores esperados vêm de spec, nunca do código atual |
| R3 | **Teste falhou = bug no código** — testes são especificação executável |
| R4 | **Proibido alterar asserts existentes** — para fazer passar |
| R5 | **Property-Based Testing** — obrigatório quando aplicável (fast-check) |

### Padrões Chave

| Pattern | Onde | Descrição |
|---|---|---|
| **DI / Command** | `jira_management/commands/` | 27 handlers recebem `CommandContext` com resources injetados |
| **Provider Strategy** | `git_triggers/` | `GitProvider` interface → `GitLabManager` / `GitHubManager` |
| **Dependency Wall** | `shared/deps.ts` | Todo import externo passa por este arquivo. ESLint enforced |
| **Resilience Stack** | `shared/http-client.ts`, `shared/llm-*.ts` | Circuit breaker + rate limiter + cache + fallback chain (6 tiers) |
| **State Persistence** | `shared/state.ts` | JSON file `~/.local/state/qa-tools/state.json` com backup recovery |
| **Store (Git-backed)** | `shared/store.ts` | SHA-keyed report cache, commits com `[skip ci]` |
| **Invariants** | `shared/invariants/` | 13 regras T-01 a T-13 + 5 I-01 a I-05 |

### Resilience Stack (LLM)

```
llm-client.ts
├── Tier: main (OpenRouter), fast (Groq), reviewer (Gemini), report (main), fallback (NVIDIA), batch (GitHub Models)
├── CircuitBreaker — estado OPEN/HALF/CLOSED
├── RateLimiter — req/min per tier
├── Cache — memória LRU + disco SHA-keyed
└── FallbackChain — main → fallback → batch
```

Todos os imports externos passam por este arquivo. ESLint `no-restricted-imports` enforced:
- `chalk`, `axios`, `zod`, `inquirer`, `ora`, `dotenv`, `csv-parser`, `yaml`, `figlet`, `cli-table3`, `cli-progress`, `glob`
